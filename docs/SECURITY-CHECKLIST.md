# Production security checklist

Use this list before exposing Fleetdock to the internet or untrusted networks.
See [SECURITY.md](../SECURITY.md) for vulnerability reporting.

## Network exposure

```text
                    Internet / corp network
                              │
                    ┌─────────▼─────────┐
                    │  TLS reverse proxy │
                    │  (443 only public) │
                    └─────────┬─────────┘
                              │
              ┌───────────────┼───────────────┐
              │               │               │
        Dashboard         API            Metadata DB
        (frontend)      (backend)        (Postgres)
                              │
              ┌───────────────┴───────────────┐
              │                               │
        Managed servers                  External DBs
        (agent → API)              (API → host:port)
```

### Control plane (dashboard + API)

- [ ] **HTTPS only** — the bundled Caddy terminates TLS and obtains a certificate. If you replace it, publish nothing but your proxy
- [ ] **Firewall** — allow 80/443; deny direct access to :8080 and to Postgres from the internet
- [ ] **Proxy headers** — `FLEETDOCK_TRUST_PROXY_HEADERS=true` **only** while :8080 is unreachable directly. Otherwise a client can spoof `X-Forwarded-For` and bypass login rate limiting; but leaving it `false` behind a proxy puts every login attempt in one bucket
- [ ] **Production mode** — `FLEETDOCK_ENV=production` (refuses default secrets)
- [ ] **Strong secrets** — generated by `install.sh`, or run `./scripts/generate-secrets.sh`; never commit `.env`
- [ ] **Back up `.env`** off-host — `FLEETDOCK_ENCRYPTION_KEY` is the only thing that can decrypt stored credentials (`fleetdock backup-config`)
- [ ] **Bootstrap admin** — change `FLEETDOCK_ADMIN_PASSWORD` after first login; use a dedicated admin email
- [ ] **Gateway** — leave external database access off unless needed; when on, open only the published port range and review CIDR allowlists

### Managed servers (agent)

- [ ] **`FLEETDOCK_PUBLIC_URL`** is the URL agents use — must be reachable from every managed host on 443, and is pinned into each agent at enrolment
- [ ] Registration tokens are **single-use** and short-lived; do not share install commands in public channels
- [ ] Agent bearer tokens are stored on disk (`state.json` on the server) — protect file permissions and restrict backup access to the state dir. The agent runs as root (it drives Docker) inside a sandboxed systemd unit; servers enrolled before the sandbox landed get it by re-running the install command
- [ ] If a server or its agent token may be compromised, **revoke** the token from the server's page (the agent is cut off at once) or **rotate** it and run the one-time re-enroll command on the server

### External database instances

- [ ] The control plane connects **directly** to external DB host:port for backups, restores, and live admin
- [ ] Ensure the API host can reach those ports (security group / firewall rule)
- [ ] Prefer private network paths (VPC peering, WireGuard, or an SSH tunnel through a bastion) over public internet
- [ ] **SSH tunnels:** use a dedicated bastion user that may only port-forward (e.g. `restrict,port-forwarding,permitopen="db:5432"` in `authorized_keys`), and a key rather than a password. The key is stored envelope-encrypted like other secrets
- [ ] The bastion's host key is pinned on the first connection (trust on first use). Check the fingerprint shown on the database server's page against the bastion, and reset the pin only when you know its key changed
- [ ] Use least-privilege DB users for instance admin credentials stored in Fleetdock
- [ ] **Notification webhooks** are fetched through an SSRF-guarded client that refuses loopback, link-local and cloud-metadata addresses at dial time. RFC1918 stays reachable for LAN targets, so keep `notification:write` restricted to trusted roles

## Authentication and sessions

- [ ] **Session cookie** — the dashboard session is an `HttpOnly`, `SameSite=Strict` cookie that script cannot read; state-changing requests must carry the `X-Fleetdock-CSRF` header. It is marked `Secure` when `FLEETDOCK_PUBLIC_URL` is `https://` or the request arrives over TLS — serve the dashboard over HTTPS
  - Keep frontend dependencies updated (`npm audit`, Dependabot)
  - Do not install untrusted browser extensions for admin users
- [ ] **API tokens** — scope tokens minimally; set expiry; revoke unused tokens
- [ ] **RBAC** — use `viewer` / `operator` roles instead of giving everyone `owner`
- [ ] **Suspend** compromised accounts immediately (sessions stop working)
- [ ] **Reset the password** to contain a stolen session — every JWT carries a token epoch that a password change increments, so all of that user's existing sessions stop working at once, without rotating `FLEETDOCK_JWT_SECRET` and logging out everyone else
- [ ] **SSO/OIDC and 2FA** — not yet available; track [ROADMAP.md](../ROADMAP.md)

## Secrets at rest

- [ ] **`FLEETDOCK_ENCRYPTION_KEY`** — unique per environment; back up rotation procedure ([OPERATIONS.md](OPERATIONS.md))
- [ ] **`FLEETDOCK_JWT_SECRET`** — unique per environment; rotation logs everyone out
- [ ] Metadata Postgres — encrypted storage at rest (provider feature or disk encryption)
- [ ] S3/R2 destination keys — encrypted in DB; agents receive presigned URLs only for backup/restore

## Metadata database

- [ ] Dedicated database user with minimum required privileges
- [ ] `sslmode=require` (or stricter) for remote Postgres
- [ ] Automated backups and tested restore ([OPERATIONS.md](OPERATIONS.md))
- [ ] No public ingress to Postgres port 5432

## Backups and object storage

- [ ] Backup buckets are **private**; presigned URLs are time-limited
- [ ] Separate IAM/bucket per environment (prod vs staging)
- [ ] Enable bucket versioning or lifecycle rules as your compliance requires

## Observability and audit

- [ ] Monitor `/healthz` and `/readyz`
- [ ] Review **Operations** log for unexpected mutating actions
- [ ] Configure notification channels for backup failures and server offline events
- [ ] Ship API JSON logs to a central system; restrict log access (credentials may appear in error messages — avoid logging request bodies)
- [ ] Connectivity and application-credential changes are written to an append-only `audit_events` table. It is **not yet exposed** through the API or dashboard — read it with `fleetdock psql` if you need the trail

## Supply chain

- [ ] Pin image tags in production (`v0.1.0`, not `latest`)
- [ ] Verify images from `ghcr.io/fleetdock/fleetdock` or build yourself from tagged source
- [ ] Enable GitHub Dependabot / renovate for the fork

## Incident response

- [ ] Document who can rotate secrets and restore metadata DB
- [ ] Know how to revoke all API tokens (JWT secret rotation or per-token revoke in UI)
- [ ] Report vulnerabilities privately per [SECURITY.md](../SECURITY.md)

## Quick pre-flight command

```bash
# Should fail in production with default secrets:
FLEETDOCK_ENV=production FLEETDOCK_DATABASE_URL=postgres://x:x@localhost/x \
  FLEETDOCK_JWT_SECRET=dev-insecure-change-me \
  FLEETDOCK_ENCRYPTION_KEY=dev-insecure-encryption-key \
  FLEETDOCK_ADMIN_PASSWORD=admin12345 \
  go run ./cmd/api
# Expected: refusing to start: FLEETDOCK_JWT_SECRET uses an insecure default
```

Run from `backend/` after cloning the repo.

## Data kept by the change journal

The data browser's undo keeps a copy of every row it edits — including the
full contents of deleted rows — in the metadata database for
`FLEETDOCK_ROW_CHANGE_RETENTION` (7 days by default). Treat metadata backups
accordingly, shorten the retention if the edited tables hold sensitive data,
or set it to `0` to keep no copies (and lose undo). The journal is readable
only by users who may browse that database.

*Compare with a backup* restores a backup into a temporary `fds_…` database
on the same server as the live one, readable by the instance's admin login,
until it is discarded or `FLEETDOCK_BACKUP_COPY_TTL` passes. Only users with
`backup:write` on the database can open one.

Schema history reads a watched database's structure (never its rows) with
the instance's admin login and keeps it in the metadata database; anyone who
may browse the database can see it. Schema comparison reads both databases
as the caller's own data login.
